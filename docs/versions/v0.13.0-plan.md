# FundPilot v0.13.0 版本计划：闭环补全

> 基线版本：v0.12.2（2026-09-22）
> 目标版本：v0.13.0
> 版本主题：补齐会静默失败、失败后无人知晓且无法自动恢复的链路；清理规范与文档债
> 推进顺序：P0 → P1 → P2（风险优先）
> 状态：待确认

## 0. 版本定位

v0.13.0 定位为**闭环补全版本**。审计结论：架构骨架健康（Modulith 模块边界有可执行校验、8 条编码规范主体合规、异常映射与数据源降级链语义正确），问题集中在三类：

1. **闭环缺口**：链路会静默失败，且失败后无人知晓、无法自动恢复。
2. **语义缺陷**：未实现的回切分支、绕过统一时间转换。
3. **文档与运维债**：产品文档过期、所有权清单缺失、迁移历史留补丁、密钥无 fail-fast。

本版本做三件事：补闭环、修语义、清债。

### 0.1 明确不在本版本范围内

**Discipline（纪律）模块的迁移与拆除已搁置，不排期。** 相关调研成果保留在附录 A，恢复时可直接使用，无需重新评估。

本版本因此不包含任何模块级功能收敛，也不以「Alerting 邮件取代卖出纪律」为目标。P0-2 中的任务失败邮件通道是**独立的可观测性补强**，与纪律去留无关。

### 0.2 运维前提（已决策）

监控栈容器已停用，编排文件在仓库中无人引用（`.github/` 工作流、`deploy/verify-release-gate.mjs`、`frontend/nginx.conf` 均不涉及）。P1-3 的处置结论：**删除 `deploy/docker-compose.monitor.yml` 与 `deploy/monitor/*`，保留全部埋点与 `prometheus` 端点**。

保留埋点的依据：`MarketDataMetrics` 有 5 处活跃调用点（`MarketDataSourceChain`、`MarketRealtimeCache`、`FundEstimateService`、`EtfIopvEstimateService`、`EastmoneyClientConfig`），`EventPublicationMetrics` 的三个指标被 `docs/operations/event-publications.md` 引用为运维手段，`JobMetricsAspect` 的指标与 `/admin`「系统监控」落库共用同一次执行。删埋点属于误删。

## 3. 问题拆分

### P0-1 兜底日期死参数链清理（已完成）

| 子任务 | 内容 | 验收 |
| --- | --- | --- |
| P0-1.1 | 删除 `TransactionCompensationCommandHandler#compensateAll(Instant fallbackDate)` 的日期入参，三个调度/接口入口不再各自构造日期 | 无入口再向补偿链路传日期 |
| P0-1.2 | `TransactionConfirmationCommandHandler#confirmPendingFor` 去掉 `fallbackDate` 入参，确认日期只取自 `transaction.effectiveTradeDate(clock.instant())` | 确认日期来源唯一 |
| P0-1.3 | 同步 4 个测试文件（`NavConfirmJobTest`、`PendingTransactionCompensationJobTest`、`NavPublishedAccountingListenerTest`、`TransactionConfirmationCommandHandlerTest`） | 定向测试通过 |

**关键决策（D1）**：`fallbackDate` 在补偿链路中不可达，无需「改成最近交易日」。补偿只处理 PENDING 流水，而 PENDING 只能由 `LedgerTransaction#placePending` 创建且强制 `trade_date` 非空；`LedgerTransaction.effectiveTradeDate(Instant fallback)` 的兜底分支仅覆盖历史空值行，被 `confirmOneWhereNavAvailable` 保留并加注释说明。

**复核更正**：原判「净值确认链路缺交易日历守卫」不成立——Alerting 侧已有交易日历守卫与逐条隔离，`NavConfirmJob` 的 cron 约束 `MON-FRI` 也非缺陷。本项由「高风险正确性缺陷」降级为「死代码清理」。

**关键决策（D2）**：不发邮件，只做后台展示——不新建通知通道，避免与 Alerting 邮件能力重叠。
**关键决策（D3）**：状态**落库持久化**而非仅存内存，重启后仍可追溯。

**顺带修复的既有缺陷**：`task` 指标标签原先只取方法名，而 `run()`（`NavConfirmJob` / `InvestmentPlanExecutionJob`）、`refreshDaily()`（`FundResearchRefreshJob` / `FundFeeRefreshJob`）、`synchronizeDaily()`（`ProductCatalogSynchronizationJob` / `TradingCalendarSynchronizationJob`）三组方法名重名，导致不同任务的指标互相覆盖。P0-2.4 先把标识统一为 `类简名.方法名` 保证唯一，再叠加 `@JobName` 提供中文展示名（注解缺失时自动回退到唯一键，不会重名）；同一 Job 类的多个方法各自标注，如「市场指标刷新·第1/2/3批」。

**实现坑（已修）**：`dayjs` 的 `utcOffset` 依赖 `utc` 插件，用到的文件必须 `dayjs.extend(utc)`（仓库其他页面均如此）。漏注册时 eslint 与 vitest 都不报错，只在浏览器运行时崩到错误边界——本项落地时踩过一次，靠启动应用实机验证才发现。

## 附录 A. Discipline 收敛（搁置，不排期）

本附录保留已完成的调研结论，供将来决策时直接使用，避免重复评估。**当前不执行任何一项。**

### A.1 恢复条件

建议在拿到「纪律实际是否被使用」的量化证据后再启动。可用 `discipline_advice` 的 `response_status` 分布，以及 `fund_transaction` 中 `discipline_advice_id` 非空的行数判断。若长期零采纳，收敛结论成立；若存在采纳记录，需评估历史交易解释性的影响。

### A.2 可行性事实

收敛之所以可行，是因为 Discipline **不承载难的技术计算**：

- `discipline/domain/advice/AdvicePolicy.java` 是纯函数（无 Spring / JPA / 状态）。
- 「逻辑破坏止损」的全部判定位于 `AdvicePolicy.java:68-76`，仅 9 行：价格跌破年线 && 周 MACD 绿柱扩大 &&（主动型 或 量能 HIGH_DROP）。
- 三个输入 `priceAboveYearLine`、`weeklyMacdState`、`volumeState` **已由 MarketData 计算并落库**：`marketdata/domain/indicator/MarketIndicator.java`、`WeeklyMacdState.java`、`VolumeState.java`，由 `MarketIndicatorRefreshCommandHandler` 刷新。

因此迁移只需**扩展提醒侧的事实来源**，不需要重建指标计算链路。
