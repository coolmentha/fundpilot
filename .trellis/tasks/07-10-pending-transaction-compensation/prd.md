# 修复待确认交易补偿

## Goal

避免定投或其他交易因净值延迟、定时任务错过或应用重启而长期停留在 `PENDING`，确保净值补齐后自动回填份额、净值和手续费。

## Background

- 定投在交易日 14:55 创建 `PENDING` 交易。
- 当晚净值任务负责写入当天累计净值，次日 03:00 的 `NavConfirmJob` 负责确认交易。
- 若 03:00 时交易日净值尚未落库，`NavConfirmService` 会保持 `PENDING` 并静默跳过。
- 后续行情任务可能补齐历史净值，但当前不会再次触发交易确认；周五漏过后可能积压到下周一。
- 手续费、份额和成交净值只在确认成功时计算，因此积压交易对应字段为空。

## Requirements

- R1：每次基金净值历史成功落库后，必须尝试确认所有已经具备交易日净值的 `PENDING` 交易。
- R2：必须保留低频定时补偿扫描，覆盖应用重启、外部数据延迟和净值落库后联动失败。
- R3：补偿确认必须按每笔交易自身的北京时间自然日查找累计净值，不得使用最新净值替代历史成交净值。
- R4：单只基金或单笔交易确认失败不得阻断其他基金的净值落库或其他待确认交易补偿。
- R5：确认成功继续统一经过 `TransactionConfirmSupport`，正确计算手续费、份额、lot 和成本单价。
- R6：现有 03:00 确认任务保留，且所有相关 cron 明确使用 `Asia/Shanghai`。
- R7：手动确认也必须按交易自身的北京时间自然日查找累计净值；该日净值缺失时明确失败，不得使用最新一期净值。
- R8：不得新增依赖，不修改数据库 schema。

## Acceptance Criteria

- [x] 交易日净值在 03:00 之后补齐时，对应 `PENDING` 交易无需等待下一个工作日即可自动确认。
- [x] 应用错过原 cron 并在稍后恢复运行后，补偿任务能够确认净值已齐备的历史交易。
- [x] 缺少交易日净值的交易仍保持 `PENDING`，不会错误使用下一交易日或最新净值。
- [x] 手动确认历史交易时使用交易发生日净值；交易日净值缺失时返回明确错误且状态不变。
- [x] 买入确认后 `nav`、`shares`、`fee` 被回填；费率缺失时 `fee=0`，不阻断确认。
- [x] 一个基金补偿失败不会回滚其他基金已成功写入的净值或已确认交易。
- [x] 定时任务时区测试、净值落库联动测试、历史交易日确认测试和既有后端测试全部通过。

## Out of Scope

- 前端新增“待确认原因”字段。
- 修改净值数据源或费率数据源。
- 自动修正已按错误净值确认的历史交易。
