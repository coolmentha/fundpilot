# 技术设计

## 方案

采用“事件后即时补偿 + 周期兜底”两层机制：

1. `DailyNavConfirmService` 和 `MarketDataFetchService` 完成净值增量写入后，调用独立的待确认交易补偿服务。
2. 新增补偿 Job，在工作日固定间隔扫描已有净值可确认的交易，覆盖重启和瞬时失败。
3. 保留 `NavConfirmJob` 03:00 主确认路径，统一显式指定上海时区。

## 边界与事务

- 净值写入事务不能与全部交易确认绑成一个大事务。
- 补偿服务按基金或独立事务执行；某笔确认异常只记录日志并继续。
- 复用 `NavConfirmService.confirmPendingTransactions` 的交易日选择与确认逻辑，不复制手续费和 lot 处理。
- `TransactionConfirmService` 改用与批量确认一致的交易日净值解析，不再读取最新一期净值。
- 为减少全表重复查询，补偿入口允许按基金触发；周期兜底可扫描全部 `PENDING`。

## 数据流

```text
外部净值 -> fund_nav_history 写入成功
         -> 触发对应基金 PENDING 补偿
         -> 按 transaction.createdDate 计算交易日
         -> 查同日 accumulatedNav
         -> TransactionConfirmSupport
         -> CONFIRMED + shares/nav/fee + lot

周期 Job -> 扫描全部 PENDING -> 同一确认路径
```

## 兼容性

- 不新增表和字段。
- 已确认、已取消交易保持幂等跳过。
- 转换交易继续遵守两腿净值齐备后原子确认。
- 既有手动确认按钮和接口路径不变，但净值口径由“最新一期”收紧为“交易发生日”。

## 风险与保护

- 风险：净值写入和确认形成循环依赖。保护：通过窄接口/独立协调服务解耦，避免市场服务直接依赖交易内部实现。
- 风险：补偿扫描重复触发。保护：事务内再次检查状态，确认逻辑保持幂等。
- 风险：单笔手续费或 lot 异常影响整批。保护：按交易/基金隔离并记录失败。

## 回滚

移除新增补偿 Job 和净值落库后的触发调用即可恢复原 03:00 单次确认机制，无数据迁移回滚。
