# 修复基金净值交易日时区错位

## Goal

确保外部净值日期统一按北京时间自然日映射为 UTC 00:00 标签，使历史净值、晚间净值确认与交易 `tradeDate` 使用同一日期口径，已有 PENDING 交易在净值具备后可被补偿确认。

## Requirements

- 东方财富 `Data_netWorthTrend.x` 的北京时间零点毫秒时间戳必须在解析边界通过 `ChinaTradingDate` 归一化，`FundNavSnapshot.navDate` 继续保持 UTC 00:00 契约。
- 已经是 UTC 00:00 的输入归一化后必须保持不变，单位净值和累计净值不得改变。
- 新增 Flyway V21 数据迁移，将存量 `fund_nav_history.nav_date` 按 `Asia/Shanghai` 自然日归一为 UTC 00:00。
- 迁移必须处理同一基金同一北京时间自然日的存量重复：保留字段最完整且更新时间最新的一行，其余行软删除，然后恢复每日唯一索引。
- 不放宽交易确认的半开区间查询，不允许用最新或次日净值替代交易发生日单位净值。
- 迁移不直接修改交易状态；应用启动后的既有补偿流程负责确认已具备净值的 PENDING 交易。
- 不新增依赖，不修改前端、认证、调度窗口或外部请求频率。

## Acceptance Criteria

- [x] 真实东方财富时间戳 `1783872000000` 解析为 `2026-07-13T00:00:00Z`。
- [x] 解析器测试同时覆盖连续交易日，且单位净值、累计净值保持原值。
- [x] 从 V20 升级到 V21 后，偏移的存量日期被归一化，重复活动行只剩一条，唯一索引仍可阻止再次重复写入。
- [x] V21 在全新 schema 上可应用，Flyway 严格校验和 Hibernate schema 校验通过。
- [x] 交易确认仍按 `[dayStart, nextDayStart)` 获取交易日单位净值。
- [x] 后端定向测试和完整测试通过。

## Notes

- 根因：东方财富将北京时间 `2026-07-13 00:00` 编码为 `2026-07-12T16:00:00Z`，旧解析器直接保存该 Instant；交易确认查询使用 `2026-07-13T00:00:00Z` 日期标签，导致同一业务日无法匹配。
- 数据流：东方财富毫秒戳 -> `EastmoneyJsParser` 归一化 -> `FundNavSnapshot` -> `fund_nav_history` -> `NavConfirmService` 按交易日查询。
