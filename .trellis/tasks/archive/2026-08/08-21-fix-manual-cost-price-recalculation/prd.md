# 修复手工成本价被交易重算覆盖

## Goal

把手工成本修正记录为“成本基准重置”事实：重置点之前的交易成本不再参与当前成本计算，
重置点之后的买入继续按新基准正常加权。

## Background

- 当前成本价是持仓的当前事实；历史交易和 FIFO lot 的取得成本是独立的历史事实。
- 现有手工修正只覆盖当前成本价，没有留下可参与账本顺序计算的重置事实。
- 旧规则要求任何后续买入都立即以当前成本继续加权，无法区分该买入在业务时间上位于手工修正之前还是之后。
- 用户确认手工修正不是永久锁定，而是一次有明确时间顺序的成本基准重置。

## Requirements

- R1：每次手工修正必须形成一条“成本修正”记录，来源为成本基准重置，创建即确认且不可撤销。
- R2：成本修正记录展示修正后的总成本、修正时持仓份额、修正后的每份成本和确认状态；
  它不能从普通“手动录入交易”入口直接创建。
- R3：计算遇到成本基准重置时，以该记录的每份成本和当时有效持仓建立新基准，
  重置前的买入金额不再参与当前成本计算。
- R4：重置后的 `INCREASE`、`TRANSFER_IN`、`INVEST` 继续按
  `新成本 = (旧成本 × 旧份额 + 本次实际投入) / 新旧份额之和` 加权。
- R5：重置时把已有全部份额纳入新成本基准；重置后的 `ADJUST_IN` 继续沿用零成本份额语义，
  卖出和 `ADJUST_OUT` 只减少用于后续加权的份额，不改变每份成本。
- R6：本次修改不改写历史交易、FIFO lot、持仓份额和建仓时间，也不改变历史已实现盈亏。
- R7：没有成本基准重置记录的存量持仓继续使用既有成本维护规则；清仓后再次买入仍以新持仓成本建立基准。
- R8：不新增依赖、数据库表或字段；复用现有交易流水和当前持仓投影。

## Acceptance Criteria

- [ ] AC1：手工修改成本价后，现有交易流水新增一条“成本修正”记录，正确展示总成本、份额、成本价和已确认状态。
- [ ] AC2：已有 100 份持仓，重置为 1.20 后再买入 20 份、实际投入 30，当前成本价为 1.25；
  重置前各笔买入金额不影响该结果。
- [ ] AC3：业务时间早于重置、但在重置后才确认的买入仍归入重置前，不覆盖手工修正结果。
- [ ] AC4：连续发生多次重置时，仅最后一次重置及其后的流水决定当前成本价。
- [ ] AC5：重置前已有的零成本调增份额被纳入新基准；重置后新增的零成本调增继续使用既有稀释规则。
- [ ] AC6：未发生重置的持仓继续按既有加权公式维护成本价；卖出、账实调减和清仓再入场语义不变。
- [ ] AC7：成本修正记录不能通过普通交易入口伪造或撤销，且不影响持仓份额、现金流统计和 FIFO lot。
- [ ] AC8：相关后端测试、前端测试、lint、构建和完整后端验证通过。

## Out of Scope

- 回填上线前发生过的手工成本修正记录；无法从现有数据可靠区分手工值与自动加权值。
- 修改历史交易或 FIFO lot 取得成本。
- 成本修正的撤销、审批、批量操作或独立页面。

## Constraints

- 当前分支为 `main`；规划阶段不修改产品代码，不执行分支或其他 Git 写操作。
- 实施前必须获得最终规划确认，并另行获得创建或切换 `hotfix/*` 分支的授权。
